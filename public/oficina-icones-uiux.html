1 Antes de Clicar: Entenda o Ecossistema

Nesta oficina, cada ferramenta tem uma função. O erro mais comum é achar que “a IA faz tudo”. Nós vamos separar o trabalho em camadas e saber exatamente onde cada coisa mora.

01IDEIASuperprompt define escopo, conteúdo e requisitos.
02IAAI Studio gera a primeira versão funcional.
03DADOSSupabase cria persistência e backend.
04CÓDIGOGitHub guarda arquivos e histórico.
05ARVercel publica e atualiza o projeto.
06DESIGNVocês redesenham conscientemente.

🤖 Google AI Studio

Gerador + ambiente de construção. Recebe o superprompt, cria arquivos, executa e mostra preview.

🗄️ Supabase

Backend. Banco PostgreSQL, autenticação, Storage e APIs.

🐙 GitHub

Repositório. Guarda código e registra alterações em commits.

▲ Vercel

Deploy. Lê o GitHub, constrói o projeto e cria uma URL pública.

Lógica pedagógica

Primeiro fazemos a infraestrutura funcionar. Só depois redesenhamos. Assim fica possível separar problema de design, dados, código e deploy.

4 Google AI Studio — Tirando o Primeiro Protótipo do Papel

O Build mode recebe uma descrição em linguagem natural, gera os arquivos e mostra um preview. Para aplicações web, o AI Studio oferece ambiente full-stack e usa React como frontend padrão.

PASSO 1

Entre no Build mode

  1. Abra o Google AI Studio.
  2. Entre em Build.
  3. Escolha a plataforma Web.
  4. Crie um projeto novo e limpo.
PASSO 2

Envie o superprompt completo

1. Copie TODO o superprompt. 2. Cole no Build mode. 3. Não retire requisitos. 4. Execute. 5. Espere o preview aparecer. 6. Leia o projeto antes de pedir mudanças.

⛔

Não comece pelo “deixa bonito”

Nesta fase, a pergunta é: o sistema existe e funciona? A personalização visual profunda vem depois do primeiro deploy.

O que é “aceitável” na primeira geração?

  • O projeto abre sem tela branca?
  • As páginas/rotas essenciais existem?
  • Os botões principais respondem?
  • Não há erros evidentes no preview?
  • O código foi dividido em componentes?
  • Existe estrutura clara para dados?
  • Desktop e mobile podem ser testados?
💡

Se quebrar

Peça para corrigir erros de build sem redesenhar nem remover requisitos. Um problema por vez.

5 Trabalhar com a IA sem Perder o Controle

Depois da primeira geração, use ciclos curtos: testar → identificar um problema → pedir uma alteração específica → testar novamente.

1 problema

Não misture banco, layout, tipografia e login no mesmo pedido.

1 instrução

Diga exatamente o que pode mudar e o que deve permanecer intacto.

1 teste

Depois da mudança, verifique se algo que funcionava deixou de funcionar.

Prompt de correção

Analise o projeto atual antes de alterar qualquer arquivo. Corrija SOMENTE o problema abaixo: [DESCREVER O PROBLEMA] Não altere design, textos, navegação ou funcionalidades já funcionando. Depois: verifique build, regressões e informe quais arquivos foram alterados.

Prompt de implementação

Implemente a funcionalidade abaixo preservando o que já funciona: [DESCREVER A FUNCIONALIDADE] Antes de editar: - identifique os arquivos envolvidos; - reutilize a arquitetura existente; - evite duplicação; - não hardcode credenciais; - não remova funcionalidades existentes. Ao final, teste o fluxo completo.

  5. Guarde a senha do banco em local seguro.
  6. Escolha a região e conclua.

PASSO 2

6.3 Pedir a integração

Integre o projeto atual ao Supabase SEM alterar a interface visual nem remover funcionalidades. 1. inspecione a arquitetura; 2. use @supabase/supabase-js; 3. crie um cliente Supabase centralizado; 4. use variáveis de ambiente para URL + Publishable key; 5. NÃO use Secret key nem service_role no frontend; 6. crie .env.example sem valores reais; 7. garanta que .env e .env.local não vão ao GitHub; 8. trate loading, erro e ausência de dados; 9. teste leitura e gravação; 10. informe arquivos alterados.

🔐

Variáveis

Em Vite/React, nomes como VITE_SUPABASE_URL e VITE_SUPABASE_PUBLISHABLE_KEY são comuns. A IA deve primeiro verificar a configuração real.

6.4 RLS — Row Level Security

A publishable key identifica o aplicativo; ela não substitui regras de acesso. Ative RLS nas tabelas e defina quem pode ler, criar, editar e excluir.

OBRIGATÓRIO

Para cada tabela, responda

  1. Quem pode ler?
  2. Quem pode escrever?
  3. Quem pode editar/excluir?

6.5 Teste mínimo

  • Crie um registro pelo sistema.
  • Recarregue.
  • O registro permanece?
  • Edite e recarregue.
  • A alteração permanece?
  • Teste exclusão, se houver.
  • Teste upload, se houver Storage.
✅

Só avance quando...

O projeto estiver lendo e gravando dados reais no Supabase.

8 Vercel — Colocando o Projeto no Ar

Conectaremos o repositório ao Vercel. Depois disso, novos pushes no Git conectado podem gerar deploys automaticamente.

PASSO 1

New Project

Entre no Vercel com a conta conectada ao GitHub e crie um novo projeto.

PASSO 2

Importe o repositório

  1. Encontre o repositório do portfólio.
  2. Clique em Import.
  3. Confira nome, framework e root directory.
  4. Não faça Deploy ainda se faltam variáveis.
PASSO 3

Environment Variables

Cadastre com os mesmos nomes do código. Exemplo Vite:

VITE_SUPABASE_URL = https://SEU-PROJETO.supabase.co VITE_SUPABASE_PUBLISHABLE_KEY = sb_publishable_...

Se houver outras variáveis legítimas no .env.example, cadastre-as também.

PASSO 4

Deploy

  1. Clique em Deploy.
  2. Acompanhe o Build.
  3. Se falhar, leia a primeira mensagem de erro real.
  4. Quando concluir, abra a URL.
PASSO 5

Teste a URL real

  • Home abre?
  • Navegação funciona?
  • Dados Supabase carregam?
  • Cadastro/edição funciona?
  • Uploads aparecem?
  • Recarregar rota funciona?
  • Mobile funciona?
🌐

Marco

Agora o sistema tem backend próprio, repositório próprio e URL própria.

9 Agora Sim: Assumir o Design — Primeiro pelo Sistema, Depois pelo Código

O superprompt já foi construído para que o portfólio não seja um template visual fechado. Ele pede design tokens, grid configurável, spacing, tipografia, cores, radius, motion e um painel “Aparência”. Portanto, antes de editar arquivos, descubram o quanto já pode ser personalizado pelo próprio sistema que vocês acabaram de criar.

✋

A IA entregou a infraestrutura. A autoria começa agora.

O objetivo não é reconstruir o sistema inteiro. É aproveitar a separação entre conteúdo + estrutura + design system + comportamento + dados para modificar a linguagem visual sem quebrar Supabase, autenticação, rotas ou funcionalidades.

9.1 Dois níveis de personalização

🎛️ NÍVEL 1 — Painel Aparência

Primeiro testem o que o próprio sistema permite alterar sem código: cores, tipografia, largura, grid, gaps, formas, movimento e linguagem. Se o superprompt foi bem executado, parte importante da autoria já deve acontecer aqui.

🧑‍💻 NÍVEL 2 — Intervenção no código

Quando a proposta visual ultrapassar os controles existentes — grid assimétrico, navegação experimental, biblioteca própria de ícones, composição especial, novos componentes — aí sim investigamos onde o Design System foi implementado.

PRIMEIRO

Entre em /admin → Aparência

Verifique se existem controles para:

  • cores;
  • tipografia;
  • largura máxima;
  • grid;
  • gaps;
  • border radius;
  • sombras;
  • motion;
  • tom de voz / nomenclatura.

Se a alteração desejada já é possível aqui, não existe razão para editar código. Use a infraestrutura configurável que o próprio projeto oferece.

DEPOIS

Quando o painel não for suficiente, investigue o código

Não suponha que “layout = um arquivo CSS”. O projeto pode ter sido implementado com:

  • CSS global;
  • CSS específico por componente;
  • CSS Modules;
  • CSS Custom Properties;
  • Tailwind;
  • ThemeProvider;
  • arquivo de tokens em TypeScript;
  • configurações persistidas em theme_config;
  • ou uma combinação dessas estratégias.

Primeiro localize. Depois altere.

9.3 Inventário antes do redesign

  • Quais páginas existem?
  • Quais componentes se repetem?
  • Existe um painel Aparência funcional?
  • Quais decisões visuais já são tokens?
  • Onde o projeto documenta o Design System?
  • Quantos tamanhos tipográficos foram gerados?
  • Quantos valores de spacing existem?
  • A navegação está clara?
  • Existem hover, focus, active, disabled, loading e error?

⚠️

Não façam “redesign por prompt”

A IA pode localizar, explicar e ajudar a implementar. Mas a decisão de design precisa ser de vocês. O aluno deve conseguir justificar o que mudou, onde mudou e por que mudou.

9.5 Pequeno acréscimo ao SUPERPROMPT — Mapa de Personalização

O superprompt já prevê uma arquitetura configurável. Acrescentem apenas este bloco para obrigar a IA a documentar os caminhos reais onde a linguagem visual foi implementada:

# MAPA DE PERSONALIZAÇÃO DO DESIGN SYSTEM Organize a implementação visual de modo que um estudante iniciante consiga localizar facilmente onde alterar o design. Evite espalhar decisões visuais por dezenas de componentes. Sempre que a arquitetura utilizada permitir, separe claramente: - tokens; - tipografia; - cores; - spacing; - grid/layout; - breakpoints; - motion; - componentes. Ao final, documente no README um: ## MAPA DE PERSONALIZAÇÃO Apresente no formato: O QUE QUERO ALTERAR → ARQUIVO/TOKEN → O QUE ELE CONTROLA Exemplo: Cor primária → [arquivo/token real] Tipografia → [arquivo/token real] Grid → [arquivo/token real] Largura máxima → [arquivo/token real] Gutters → [arquivo/token real] Spacing → [arquivo/token real] Border radius → [arquivo/token real] Ícones → [arquivo/componente real] Breakpoints → [arquivo/regra real] Não invente nomes fixos de arquivos antes da implementação. Documente os caminhos REAIS utilizados no projeto gerado.

✅

O que queremos encontrar no README

Algo como: “Grid → src/styles/layout.css → controla colunas e container”, ou “Cores → src/theme/tokens.ts → controla tokens semânticos”. Os nomes podem variar; o importante é o mapa refletir o projeto REAL.

13 Antigravity, VS Code ou ChatGPT — Localizar, Compreender e Alterar com Precisão

Depois que o sistema está no ar e a autoria visual começa, podemos usar um copiloto de código. Mas sua função agora é diferente: ele não deve reinventar o projeto. Ele deve nos ajudar a compreender a arquitetura existente e executar alterações delimitadas.

🧭

Regra-mãe desta fase

Não comece pedindo “altere o CSS”. Comece pedindo: “onde este projeto implementa o Design System e o layout?” Só depois autorize a edição.

13.1 Três caminhos possíveis

🛰️ Google Antigravity

Útil quando queremos um agente inspecionando o projeto, planejando alterações e atuando sobre arquivos reais.

💻 Visual Studio Code + Copilot

O editor mantém o workspace visível; os recursos de IA podem responder sobre arquivos e ajudar a editar o código.

🤖 ChatGPT + Codex

Útil para analisar projetos, explicar arquitetura, localizar arquivos e executar/refatorar tarefas de código.

13.2 Antes de qualquer edição: encontre o Design System REAL

Analise o projeto REAL que foi gerado a partir do nosso superprompt. Quero começar a personalizar o DESIGN SYSTEM. NÃO ALTERE NADA AINDA. Localize no projeto onde estão definidos: 1. cores; 2. tipografia; 3. spacing; 4. número de colunas; 5. largura máxima do conteúdo; 6. margins; 7. gutters; 8. gaps; 9. breakpoints; 10. grid dos projetos; 11. proporção/formato dos cards; 12. ícones; 13. motion. Verifique qual estratégia o projeto realmente usa: - CSS global; - CSS por componente; - CSS Modules; - CSS Custom Properties; - Tailwind; - ThemeProvider; - tokens em TypeScript/JavaScript; - theme_config vindo do Supabase; - ou outro mecanismo. Para cada item, responda: O QUE QUERO ALTERAR → ARQUIVO/TOKEN REAL → O QUE ELE CONTROLA Não invente nomes de arquivos. Não faça nenhuma alteração ainda.

💡

Por que fazemos isso?

Porque dois alunos podem ter usado o mesmo superprompt e receber arquiteturas diferentes. A lógica pedagógica precisa sobreviver à implementação: localizar antes de editar.

13.3 Exemplo — “Vamos mexer no layout do projeto”

Situação

Vocês decidiram aplicar o sistema de grid estudado na oficina: 12 colunas no desktop, 8 no tablet e 4 no mobile. Talvez isso esteja em um CSS. Talvez esteja em Tailwind. Talvez esteja em tokens ou num componente de layout. Primeiro descobrimos.

PASSO 1 — LOCALIZAR

Peça um mapa do layout atual

Quero alterar o LAYOUT deste projeto. Antes de mudar qualquer coisa: 1. identifique qual arquivo/componente renderiza a página de Projetos; 2. identifique onde o layout visual dessa página é controlado; 3. verifique se usa CSS, CSS Modules, Tailwind, ThemeProvider, tokens ou outro sistema; 4. localize onde estão definidos: - grid; - largura máxima; - margins; - gutters; - gaps; - breakpoints; - disposição dos cards; 5. diga se algum desses valores vem do painel Aparência ou do Supabase. NÃO ALTERE NADA AINDA. Responda no formato: ARQUIVO/TOKEN → REGRA ATUAL → O QUE CONTROLA.

PASSO 2 — DECIDIR

Compare a arquitetura atual com a intenção de design

Minha decisão de design será: DESKTOP - 12 colunas - margin lateral 80px - gutter 24px TABLET - 8 colunas - margin 32px - gutter 24px MOBILE - 4 colunas - margin 16px - gutter 16px Antes de editar, diga quais regras/tokens precisam mudar e quais NÃO precisam mudar. Preserve: - Supabase; - conteúdo; - rotas; - autenticação; - funcionalidades; - dados.

PASSO 3 — ALTERAR

Autorize a menor alteração possível

Agora implemente APENAS esse novo sistema de layout. REGRAS: - reutilize a arquitetura existente; - prefira alterar tokens/regras centrais em vez de espalhar novos valores; - não reescreva componentes sem necessidade; - não altere conteúdo; - não altere backend; - não altere rotas; - preserve acessibilidade; - preserve estados e funcionalidades existentes; - não faça nenhuma outra mudança estética.

PASSO 4 — ENTENDER

Peça os arquivos e a explicação

Ao terminar: 1. liste todos os arquivos alterados; 2. diga o caminho exato de cada arquivo; 3. explique o que mudou no layout; 4. mostre quais tokens/regras foram alterados; 5. se eu precisar editar manualmente, forneça o arquivo COMPLETO; 6. teste desktop, tablet e mobile; 7. valide o build; 8. informe qualquer regressão ou problema restante.

13.4 Exemplo — Biblioteca própria de ícones

Situação
